# Holochain 0.2 → 0.7 upgrade (branch `hdk-7.1`)

This branch moves Where from Holochain 0.2 (hdk 0.2.6, `@holochain/client` 0.16,
`@lightningrodlabs/we-applet`) to **Holochain 0.7.1** (hdk 0.7.1 / hdi 0.8.1,
`@holochain/client` 0.21, `@theweave/api` 0.7) and turns the We applet into a
**Moss Tool**. It followed the official upgrade guides on developer.holochain.org
(0.3 → 0.7) plus the field notes in `../ai-tools/skills/upgrade-holochain-0.7`.

## Hard break: no data migration

0.7 cannot read older databases and the **DNA hashes have changed**, so agents on
the old and new versions form disjoint networks. Clear conductor state before running
(`npm run clean:hc`); shipped installs need a fresh profile. Publish the Tool under a
new `versionBranch` in the Moss Tool list.

## Zome read API: `ZomeFnInput<T>`

Every read-only zome function takes `ZomeFnInput<T> = { input: T, local?: boolean }`
(shared crate `dna/zomes/zome_fn_input`, same shape as presence and the open-dev
profiles zome). `local` defaults to `true`: the call only reads what the conductor
already holds (`GetStrategy::Local`); `local: false` goes to the network. Write
functions keep their plain inputs; the lookups they need try local first and fall back
to the network.

On the UI side every ZVM probe takes a `GetStrategy`. lit-happ 0.36 initializes the
perspective from local data first (`initializePerspectiveFromLocal`) and the app then
refreshes from the network (`perspectiveInitializedFromNetwork`).

The TS bindings are generated by zits 1.17.2 (`npm run build:bindings`);
`scripts/fix-bindings.py` restores the `ZomeFnInput<T>` parameter types that zits
flattens, and `scripts/ts-bindings.sh` fixes the tagged-enum shape it emits.

## Notable 0.7 changes hit

- `hdk_entry_defs` → `hdk_entry_types`, `entry_def` → `entry_type`; the entry helper
  macro needs `holochain_serialized_bytes` as a direct dependency of every zome.
- `get_links(LinkQuery::try_new(..)?, strategy)`, `delete_link(ah, GetOptions)`,
  `TypedPath` carries a `GetStrategy` (`with_strategy`), `GetOptions::local()/network()`.
- `remote_signal` → `send_remote_signal`; cap grants are
  `CapGrant::new_zome_call_grant(tag, GrantConstraint::Unrestricted, functions)` (0.7.1).
- `agent_latest_pubkey` → `agent_initial_pubkey`.
- Every coordinator zome re-exports zdk's `zome_core` (`get_zome_info`, `get_dna_info`,
  ...): `@ddd-qc/lit-happ` 0.36 calls them while a DVM initializes and otherwise rejects
  the init, so the Tool rendered nothing.
- In Moss dev mode (`source.type: localhost`) the Tool calls `initializeHotReload()`
  before `WeaveClient.connect()` (see `moss-tool/src/index.ts`); without it `connect()`
  waits forever for `applet-iframe-ready` and the Tool shows a blank page, no error.
- Root `tsconfig.json` is `module`/`target` ES2022 (needed for `import.meta.env`).
- Building the wasms outside holonix needs `-C link-arg=--import-undefined` (newer
  rustc rejects the undefined host-function symbols). `npm run build:zome` sets it.
- `hc sandbox` has no `network …` subcommand any more; local bootstrap/relay is
  conductor config (one `kitsune2-bootstrap-srv-iroh-relay` serves both).
- client 0.21: `AppAgentClient` → `AppClient`, signals arrive as `Signal`
  (`type: "app"`), cell addresses are `cell.address.agentId/dnaId` in cell-proxy.
- `@theweave/api` 0.7: `HrlWithContext` → `WAL`, `getAttachableInfo` → `getAssetInfo`,
  `attachableInfo/openHrl/hrlToClipboard/userSelectHrl` → `assets.*`/`openAsset`,
  block views and `bindAsset` are gone, `AppletInfo.groupsIds` → `groupsHashes`.

## Verified

- all 8 wasms build and link; `hc 0.7.1` packs both DNAs, the three happs and the
  Tool webhapp.
- `scripts/smoke-test.mjs` (`npm run smoke` against a running sandbox) installs the
  happ in a real 0.7.1 conductor and exercises `zPlayset`, `zWhere` (local and network
  reads, sessions, heres, hide/unhide, delete, remote signal to self) and `profiles`.
- `webcomponents`, `webapp.ludotheque`, `webapp` and `moss-tool` typecheck and build.
